# 响应式侧边导航改造设计

## 背景

当前壳层导航在窄宽度下分成两段响应式处理：

- `1040px` 以下通过 CSS 直接隐藏菜单文字、箭头和子菜单
- `720px` 以下直接隐藏整个侧边栏

这个实现有一个核心断层：视觉上看起来像“收起”，但交互上并没有进入真正的收起态。`frontend/src/layouts/AppLayout.vue` 里只有 `isSidebarCollapsed` 为真时才会渲染并启用 `sidebar-flyout`，而 `frontend/src/styles/shell.css` 在 `1040px` 以下只是隐藏内容，没有同步切换导航行为。

结果就是在平板和窄桌面区间里会出现下面的问题：

- 侧边栏只剩图标
- 子菜单不能稳定点击
- 用户无法靠滚动或展开完成导航
- 视觉状态和实际状态不一致，后续维护容易继续出错

## 目标

这次改造只解决壳层导航在桌面、平板、手机三段宽度下的可用性闭环，不扩大到菜单数据结构、权限链路或业务页面布局重构。

完成后需要满足：

- 桌面宽度保留当前完整侧边栏体验
- 中窄屏宽度进入真正的收起态，而不是仅用 CSS 把文字藏掉
- 手机宽度改为抽屉导航，避免常驻图标栏在触屏下难以操作
- 同一份菜单树在三段布局里保持一致的可达性和高亮规则
- 不破坏现有标签页、面包屑、权限过滤和当前路由高亮逻辑

## 非目标

这轮明确不做：

- 不重写 IAM 菜单来源
- 不调整菜单权限判定接口
- 不重构整个 `AppLayout.vue` 为多个新组件，除非实现中发现拆分是必要的小范围整理
- 不扩展新的移动端业务页面布局体系
- 不引入新的 UI 库或响应式框架

## 方案对比

### 方案 A：继续保留“假收起”，只补一点 hover 或滚动样式

优点：

- 改动最少

缺点：

- 仍然依赖“视觉收起”和“逻辑收起”分离
- 对触屏和窄屏点击问题改善有限
- 后续极易再次出现“看得到但点不到”的状态

结论：

- 不采用

### 方案 B：`1040px` 以下统一进入真正的收起态，`720px` 以下切抽屉

优点：

- 能复用现有 `isSidebarCollapsed` 和 flyout 逻辑
- 平板、小笔记本、手机三段都有明确交互模型
- 改动集中在壳层和样式层，回归面相对可控

缺点：

- 需要把“手动收起”和“响应式收起”拆开建模
- 需要补一个手机端抽屉入口与开关逻辑

结论：

- 采用

### 方案 C：所有窄屏都统一改成抽屉

优点：

- 触屏体验简单直接

缺点：

- 平板和小笔记本也失去常驻导航，操作效率下降
- 对当前桌面应用风格变化过大

结论：

- 作为兜底备选，不作为本轮主方案

## 最终设计

### 1. 断点策略

导航布局改成三段式：

- `> 1040px`
  - 使用完整侧边栏
  - 支持现有手动收起按钮
- `721px - 1040px`
  - 自动进入真正的紧凑侧栏
  - 保留图标列
  - 一级菜单点击或聚焦后显示可交互的浮出菜单
- `<= 720px`
  - 隐藏常驻侧边栏
  - 在顶部栏提供菜单入口
  - 使用抽屉承载完整导航

这里的关键不是“隐藏什么元素”，而是每个区间都要有完整可用的导航模型。

### 2. 状态建模

当前只有一个 `isSidebarCollapsed`，它同时承担：

- 用户主动点击收起
- 视觉控制
- flyout 渲染条件

这会让响应式场景和用户手动场景互相混淆。改造后需要拆成两个概念：

- `manualSidebarCollapsed`
  - 只记录桌面场景下用户主动点击收起
- `isCompactViewport`
  - 根据视口宽度判断是否处于中窄屏区间

最终视图实际使用的收起态应为：

- `isSidebarCollapsed = manualSidebarCollapsed || isCompactViewport`

手机抽屉再单独维护：

- `isMobileViewport`
- `mobileNavVisible`

这样可以保证：

- 中窄屏自动进入真收起态
- 桌面仍然保留用户偏好收起能力
- 手机不会错误复用桌面收起逻辑

### 3. 侧边栏交互规则

#### 桌面完整态

- 保持现有多级展开逻辑
- 保持 `openKeys` 与当前路由祖先链同步

#### 中窄屏紧凑态

- 侧边栏仅保留一级图标入口
- 二三级菜单不在栏内内联展开
- 有子节点的一级菜单通过 flyout 展示完整可点击内容
- 没有子节点的一级菜单仍然直接跳转
- flyout 必须支持鼠标点击、键盘 focus 和容器内滚动

重点是这一段必须真的走 `sidebar-collapsed` 语义，而不是只有视觉上的图标化。

#### 手机抽屉态

- 顶部栏新增菜单按钮
- 点击打开抽屉
- 抽屉里显示完整导航树，而不是图标模式
- 点击叶子菜单后自动关闭抽屉并跳转
- 切换路由后抽屉应自动关闭，避免遮挡主内容

### 4. 模板结构调整

`AppLayout.vue` 需要补的不是整页重写，而是最小闭环增强：

- 顶部栏增加移动端菜单按钮
- 侧边栏渲染条件依赖实际布局模式
- 抽屉中复用同一份菜单数据和高亮判断

优先选择：

- 提炼一个局部复用的导航渲染片段或小组件

避免：

- 复制两套不同的菜单树模板，导致后续一边修一边漏

如果直接抽组件成本过高，也可以先在同文件内抽成局部渲染块，但目标仍然是减少桌面侧栏与手机抽屉的模板分叉。

### 5. 样式策略

`shell.css` 需要从“通过媒体查询直接隐藏内容”改成“媒体查询只决定布局模式”：

- `1040px` 以下不再单独把 `.label-text`、`.submenu-l2`、`.submenu-l3` 强制 `display: none`
- 这些隐藏规则应统一依赖 `.sidebar-collapsed`
- `720px` 以下不再只剩“隐藏侧边栏”这一条，需要同时给顶部按钮和抽屉样式留出口

样式上还需要确认：

- flyout 不会被父容器裁剪
- 窄屏时侧边栏滚动区仍可滚动
- 抽屉内长菜单可以完整滚动
- 顶部栏在手机宽度下仍能容纳菜单按钮、面包屑、租户信息和用户操作

### 6. 可访问性与输入方式

本轮虽然不是专项无障碍改造，但至少要保证：

- 图标按钮有明确 `aria-label`
- flyout 可以通过 focus 打开，不只依赖 hover
- 抽屉打开后可以关闭
- 菜单在触屏场景不依赖 hover 才能访问

### 7. 回归边界

这次改造最容易带出的问题不在“导航能不能显示”，而在壳层副作用，因此验收要覆盖：

- 当前路由对应菜单仍然高亮
- 祖先菜单展开逻辑不回退
- 标签页新增、切换、关闭不受影响
- 面包屑仍然正确
- 登录后首次进页面与刷新恢复后的导航表现一致
- 手机抽屉打开后切路由能自动关闭

## 受影响文件

预计会改动：

- `frontend/src/layouts/AppLayout.vue`
  - 补响应式状态、移动端抽屉开关、导航复用逻辑
- `frontend/src/styles/shell.css`
  - 调整断点策略、紧凑态样式来源、移动端顶部入口与抽屉样式

可能小范围补充：

- `frontend/scripts/verify-sidebar-active-ancestor-open.mjs`
  - 如果现有脚本只覆盖桌面壳层，需补中窄屏或手机态断言
- `frontend/package.json`
  - 仅在需要新增校验脚本命令时修改

## 验证策略

至少验证下面几类场景：

### 1. 桌面

- 全宽下完整菜单正常显示
- 手动收起后 flyout 可用
- 展开和高亮不回退

### 2. 中窄屏

- 自动进入真收起态
- 一级图标可点
- flyout 可点、可滚、可跳转
- 不再出现“只剩图标但无法访问子菜单”

### 3. 手机

- 菜单按钮可见
- 抽屉能打开和关闭
- 抽屉内导航可滚动
- 选中叶子菜单后关闭抽屉并完成路由跳转

### 4. 回归

- `npm run build`
- 现有导航相关校验脚本
- 如有新增响应式校验脚本，确保覆盖中窄屏与手机态

## 风险与控制

### 风险 1：响应式状态与手动状态互相覆盖

控制方式：

- 明确拆分 `manualSidebarCollapsed`、`isCompactViewport`、`isMobileViewport`

### 风险 2：桌面和手机模板复制后逻辑不一致

控制方式：

- 优先复用同一份菜单渲染逻辑和点击处理函数

### 风险 3：flyout 或抽屉引入新的滚动和遮挡问题

控制方式：

- 回归验证时专门检查父容器 overflow、z-index 和移动端滚动区

## 验收标准

满足下面条件才算完成：

- `1040px` 以下不再依赖“只隐藏文字”的假收起实现
- `721px - 1040px` 区间里二三级菜单稳定可访问
- `720px` 以下存在可操作的抽屉导航入口
- 桌面态、紧凑态、手机态都能到达当前 IAM 列权限页面及其相邻系统页面
- 导航改造不破坏现有高亮、标签页和面包屑行为
